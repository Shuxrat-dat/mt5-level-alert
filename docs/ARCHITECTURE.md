# Архитектура системы

## 1. Обзор

```
                                INTERNET
                                    |
                          Coordination Backend
                        (Node.js + SQLite, 1 сервер)
                                    |
                    ┌───────────────┴───────────────┐
                    |                                |
                  PC1 (priority=1)                 PC2 (priority=2)
                  MT5 + EA                          MT5 + EA
                    |                                |
                    └───────────────┬───────────────┘
                                    |
                              Telegram Bot API
                                    |
                             Telegram-группа
```

Система рассчитана на **произвольное число ПК** (в текущей поставке — 2, PC1 и
PC2), приоритет — это просто число: чем меньше, тем выше приоритет. Если
понадобится третий ПК — это одна команда `register-device`, без изменений кода.

Backend — единственный "источник истины". EA на каждом ПК не принимает решений
друг о друге напрямую (никакого P2P) — все решения (кто ACTIVE, какие уровни
существуют, было ли уже отправлено уведомление) принимает backend, потому что
только он может гарантировать атомарность (см. раздел 3).

## 2. Почему backend вообще нужен

Технически можно было бы попытаться сделать так, чтобы ПК сами договаривались,
кто ACTIVE. Проблема в том, что без общего атомарного хранилища **невозможно
исключить split-brain**: если PC1 и PC2 одновременно решат "второй не отвечает
— беру роль на себя", оба начнут слать уведомления. Единственный надёжный
способ этого избежать — атомарная операция compare-and-swap в одном месте,
которую видят оба клиента. Это и есть backend + SQLite-транзакция.

Backend **не отправляет ордера, не торгует и не имеет доступа к счёту** — это
чистый координационный слой: кто сейчас главный, какие линии нарисованы, что
уже отправлено в Telegram.

## 3. Leader election / distributed lease

Таблица `cluster_state` — синглтон-строка (`id=1`):

```sql
active_pc_id    TEXT     -- кто сейчас ACTIVE
lease_id        TEXT     -- текущая "аренда" роли (UUID)
lease_until_ms  INTEGER  -- когда аренда истекает
```

Каждый EA каждые `HEARTBEAT_INTERVAL_SEC` секунд (по умолчанию 5) шлёт
`POST /api/heartbeat`. Внутри одной SQLite-транзакции backend:

1. Обновляет `last_seen_ms` для звонящего ПК.
2. Строит список "живых" ПК — тех, чей heartbeat не старше
   `FAILOVER_TIMEOUT_SEC` (по умолчанию 15с = 3× интервала, чтобы пережить
   обычный джиттер сети без ложного failover).
3. Выбирает **желаемого** ACTIVE: среди живых — с наименьшим priority.
4. Если желаемый ≠ текущий ACTIVE — выпускает новую аренду (CAS-обновление
   `UPDATE ... WHERE lease_id = <старый>`), иначе просто продлевает аренду,
   если звонящий и есть текущий ACTIVE.

### Почему это не даёт split-brain

Node.js однопоточный, а better-sqlite3 — **синхронный** драйвер. Пока
выполняется функция `applyHeartbeatAndElect`, ни один другой HTTP-запрос
физически не может начать выполняться параллельно (событийный цикл занят).
Обёртка в `db.transaction()` — это дополнительная гарантия "всё или ничего"
на случай падения процесса посреди операции, и явная документация того, что
если вы захотите позже перейти на Postgres с несколькими воркерами — CAS по
`lease_id` в `WHERE`-условии обязателен и уже на месте.

### Anti-flapping (защита от дребезга)

Наивная логика "у кого приоритет выше — тот и ACTIVE" плохая: если PC1 имеет
нестабильное подключение (появляется/пропадает каждые пару секунд), он будет
постоянно выхватывать роль у здорового PC2 и тут же её терять — куча дублей и
пропусков.

Правило: **если сейчас есть здоровый (живой) ACTIVE, любой другой ПК должен
непрерывно быть живым минимум `PROMOTION_STABLE_SEC` секунд (по умолчанию 10),
прежде чем сможет его вытеснить.** Сам действующий ACTIVE всегда может
подтверждать роль без этого ограничения.

Если здорового ACTIVE сейчас нет (первый запуск кластера, либо прежний ACTIVE
реально не отвечает дольше `FAILOVER_TIMEOUT_SEC`) — защищать нечего, и любой
живой ПК немедленно становится ACTIVE. Это даёт: мгновенный старт при первом
включении, быстрое восстановление при реальном падении, и отсутствие дребезга
при нестабильной сети.

### Сценарии из ТЗ

| Сценарий | Результат |
|---|---|
| PC1 и PC2 включены одновременно | Первый, чей heartbeat дошёл раньше, становится ACTIVE; если это оказался PC2 — как только PC1 «докажет» стабильность (10с), он вытеснит PC2 согласно приоритету |
| PC1 выключен | PC2 становится ACTIVE не позже чем через `FAILOVER_TIMEOUT_SEC` после последнего heartbeat PC1 |
| PC1 снова включился | PC2 остаётся ACTIVE ещё `PROMOTION_STABLE_SEC`, затем PC1 забирает роль обратно |
| Backend временно недоступен | EA сохраняет последнюю известную роль и не переходит в ACTIVE самопроизвольно (см. `docs/TROUBLESHOOTING.md`) |

## 4. Идемпотентность уведомлений (защита от дублей)

Это самая критичная часть системы, поэтому механизм — избыточно простой и
проверяемый.

Таблица `level_state` хранит последнее отправленное событие для каждого
уровня:

```sql
level_id, last_event_type, last_event_price, last_event_at_ms, cycle_id
```

`POST /api/notify/trigger` вызывается EA только когда: (а) EA считает себя
ACTIVE, и (б) локальная state machine цены (см. раздел 6) решила, что
произошло реальное событие. Backend делает следующее в одной транзакции:

1. **Проверка аренды.** `active_pc_id == pc_id AND lease_id == <из запроса>
   AND lease_until_ms > now`. Если нет — `409 not_active`, сообщение не
   отправляется. Это отсекает "залипшую" роль: если PC1 только что потерял
   ACTIVE, но ещё не получил следующий heartbeat с обновлением, его попытка
   отправить будет отклонена сервером, даже если сам PC1 ещё думает, что он
   ACTIVE.
2. **Дедупликация.** Если `event_type` совпадает с `last_event_type` и
   прошло меньше `NOTIFICATION_MIN_INTERVAL_SEC` (по умолчанию 3с) — это
   дубль, Telegram не дёргаем, отвечаем `{"status":"duplicate"}`.
3. **CAS-захват слота.** Иначе — атомарно инкрементируем `cycle_id`
   (`UPDATE ... WHERE cycle_id = <старый>`). Если кто-то другой успел раньше
   (гонка при переключении ролей) — `changes=0`, тоже дубль.
4. Только победитель CAS реально идёт в Telegram (см. раздел 5).

### Почему этого достаточно против дублей при failover

Худший случай: PC1 был ACTIVE, отправил `TOUCH`, через 2 секунды упал. PC2
стал ACTIVE. PC2 не знает локально, что PC1 уже отправлял `TOUCH` — но при
следующем heartbeat backend вернёт ему в списке уровней поле
`last_event_type: "TOUCH"`, и EA на PC2 бутстрапит свою локальную state
machine этим значением (раздел 6) — то есть PC2 просто не попытается снова
отправить `TOUCH` для этого уровня, пока цена не уйдёт и не вернётся (RESET).
А если PC2 всё-таки попытается (например, оба процесса были ACTIVE доли
секунды во время смены аренды) — сервер отклонит дубль по правилу выше. Два
независимых уровня защиты: (1) EA не пытается повторно, (2) даже если
попытается — backend не пропустит.

## 5. Отправка Telegram

Backend, не EA, хранит `TELEGRAM_BOT_TOKEN` и реально дёргает Telegram Bot
API. Это осознанное архитектурное решение:

- Токен никогда не появляется на Windows-машинах и никогда не попадёт в git
  по невнимательности.
- "Захват слота" (шаг 3 выше) и "отправка" разделены: захват — синхронная
  SQLite-транзакция, отправка — асинхронный сетевой вызов вне транзакции
  (better-sqlite3 не поддерживает async внутри транзакции). Если сама
  отправка в Telegram упадёт (Telegram недоступен) — слот уже захвачен (не
  будет второй попытки от другого события), а `retryWorker.ts` каждые 30
  секунд подбирает записи со статусом `failed` и досылает их (до 5 попыток,
  не дольше часа) — это защита от сценария "Telegram API временно
  недоступен" из ТЗ.

Бот добавляется в Telegram-группу (не личный чат) — `TELEGRAM_CHAT_ID` в этом
случае отрицательное число (id группы). Один бот, одна группа — все уровни с
обоих терминалов идут туда, независимо от того, какой ПК сейчас ACTIVE (см.
`docs/INSTALL.md`, шаг получения `CHAT_ID` для группы).

## 6. Мультитаймфрейм: M5 / M15 / M30 / H1 / H4 / D1 / W1 / MN1

### Ключевое наблюдение

У XAUUSD одна цена вне зависимости от того, на каком таймфрейме открыт график
— таймфрейм влияет только на то, где физически нарисованы линии объектов. Это
сильно упрощает архитектуру:

- **`OnTick` вызывается один раз** (EA прикреплён к одному графику, например
  M5, и получает поток тиков от него) и на каждый тик прогоняет
  price-state-machine по всем закешированным уровням сразу, независимо от
  того, с какого таймфрейма они пришли.
- **Сканирование линий (объектов)** — отдельная, гораздо более редкая
  операция (раз в `HeartbeatIntervalSec`), и вот она уже честно идёт по
  каждому включённому таймфрейму отдельно, потому что линии физически лежат
  на разных графиках.

### Как EA получает доступ к 8 графикам сразу

При старте (`OnInit`) EA для каждого включённого таймфрейма ищет уже открытый
график этого символа+периода через `ChartFirst()/ChartNext()`; если не
находит — открывает сам через `ChartOpen(symbol, timeframe)`. Это создаёт
фоновые вкладки графиков в терминале (стандартная техника для
мультитаймфреймовых EA/индикаторов) — их не нужно держать на экране, EA читает
и пишет объекты по `chart_id` напрямую. `EnsureChartsOpen()` перепроверяет это
на каждом таймере — если пользователь случайно закрыл вкладку, она
переоткроется автоматически.

**Важно:** EA прикрепляется только один раз, к любому из графиков
(рекомендуется M5) — не нужно (и не следует) вручную цеплять его повторно на
остальные 7 фоновых графиков.

### Формат данных

Уровень теперь привязан к паре `(symbol, timeframe)`, а не только к `symbol`.
`level_id` (UUID) — уникален глобально, не зависит от таймфрейма. Если
нарисовать линию на одной и той же цене одновременно на M5 и на H1 — это
будут два разных уровня с двумя независимыми уведомлениями (так и задумано:
значимость уровня зависит от таймфрейма, на котором вы его отметили).

`POST /api/heartbeat` больше не принимает `timeframe` — один вызов возвращает
уровни сразу по всем таймфреймам для символа (объём данных крошечный, десятки
уровней максимум), EA сам раскладывает их по нужным графикам, используя поле
`timeframe` в каждом объекте уровня.

`POST /api/levels/sync` принимает `timeframe` на уровне каждого элемента
массива `levels[]` — один batched-вызов может одновременно сообщить об
изменениях сразу на нескольких таймфреймах.

## 7. Синхронизация уровней между ПК

1. Пользователь рисует линию (`OBJ_HLINE`) на любом из графиков на PC1.
2. EA на следующем скане (до `HeartbeatIntervalSec` секунд) обнаруживает
   объект без префикса `LVL_`, генерирует UUID v4, переименовывает объект на
   месте в `LVL_<uuid>` (используется `ObjectSetString(...,OBJPROP_NAME,
   ...)` — родная функция MT5 для переименования, а не удаление+пересоздание)
   и отправляет `upsert` на backend.
3. PC2 при следующем heartbeat получает этот уровень в списке (с полем
   `timeframe`) и, не найдя у себя объекта с таким `level_id`, создаёт
   `OBJ_HLINE` с именем `LVL_<uuid>` на соответствующем локальном графике —
   линия появляется автоматически, без участия пользователя.
4. Если линию подвинуть — на следующем скане обнаруживается изменение цены
   (порог — размер пункта символа, чтобы игнорировать шум), уходит `upsert` с
   тем же `level_id`.
5. Если линию удалить — объект пропадает из списка `ObjectsTotal(...)`,
   backend получает `delete` (мягкое удаление, `deleted=1`), и при следующем
   heartbeat все остальные ПК удаляют у себя зеркальную копию.

`level_id` устойчив к переименованию объекта пользователем в MT5 (после
первого захвата имя всегда содержит UUID) — источник истины сервер, а не имя
MT5-объекта.

## 8. Источники истины

| Что | Где хранится | Почему |
|---|---|---|
| Кто сейчас ACTIVE | `cluster_state` на backend | Единственное место, где возможен атомарный CAS |
| Список уровней | `levels` на backend | Общий для всех ПК, backend — единственный, кто видит оба терминала сразу |
| Было ли уже отправлено уведомление | `level_state` на backend | Та же причина — нужен CAS, недоступный локально на ПК |
| Локальное текущее состояние (APPROACHING/TOUCHED/...) | В памяти каждого EA | Не критично для консистентности — при потере ACTIVE-роли новый ACTIVE бутстрапится из `last_event_type`, присланного backend'ом |

## 9. Надёжность: список того, что явно обработано

- **Идемпотентность** — раздел 4.
- **Race conditions** при одновременных heartbeat — синхронная однопоточная
  модель Node.js + `db.transaction()`.
- **Distributed lock** — CAS по `lease_id`, раздел 3.
- **Stale heartbeat** — `FAILOVER_TIMEOUT_SEC`.
- **Clock differences** — backend использует только свои временные метки
  (`Date.now()` на сервере) для всех критичных сравнений (аренда, дедуп);
  часы на клиентских ПК нигде не участвуют в consensus-логике, только в
  логах.
- **Network failure / backend недоступен** — EA не считает себя ACTIVE по
  умолчанию, сохраняет последнюю известную роль и логирует `[WARN] Backend
  unavailable`; см. `TROUBLESHOOTING.md`.
- **Duplicate events / retry** — раздел 4 и 5 (`retryWorker.ts`).
- **Telegram timeout** — таймаут 8с + до 3 попыток inline + до 5 попыток в
  фоновом воркере.
- **Corrupted state** — `cluster_state` — синглтон с `CHECK(id=1)`, SQLite
  WAL-режим включён (устойчив к внезапному отключению питания на сервере).

## 10. Известные ограничения (честно)

- Если пользователь независимо нарисует линию на одной и той же цене на
  обоих ПК до первой синхронизации — получится два разных `level_id` и,
  соответственно, два уведомления. Рекомендация: рисовать линии на одном ПК и
  давать им время смигрировать (до `HeartbeatIntervalSec` секунд).
- Между реальным кросс/тач-событием и подтверждённой отправкой в Telegram
  есть сетевая задержка (обычно < 1с). Если именно в этот момент backend
  временно недоступен, конкретное событие может быть потеряно (EA не хранит
  очередь на диске) — компромисс в пользу простоты; см. раздел 9 и
  `TROUBLESHOOTING.md` для смягчения (используйте VPS с высоким аптаймом, не
  домашний роутер).
- SQLite — однопроцессный писатель. Для 2 (и даже 10+) ПК с heartbeat раз в 5
  секунд нагрузка ничтожна (кратно меньше 1 запроса в секунду), апгрейд до
  Postgres не требуется, но код к этому готов (CAS через `WHERE`, а не через
  `SELECT FOR UPDATE`, что одинаково хорошо работает в обеих СУБД).
